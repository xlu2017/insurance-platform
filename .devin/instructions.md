# Devin Instructions

## Provider Confidentiality and Abstraction Requirement

The document-analysis provider is an internal implementation detail.
Do not expose the provider name, model family, API host, file identifiers, model identifiers, or provider-specific terminology through any customer-facing or publicly accessible surface.

### 1. Customer-facing language must be provider-neutral

Use language such as:

- "Analyzing documents"
- "Secure document processing"
- "Document analysis in progress"
- "File ready for analysis"
- "This file could not be processed"
- "This file is too large for document analysis"
- "This file type is not currently supported"
- "Document analysis temporarily unavailable"

Do not display provider names, model identifiers, provider file identifiers, provider model IDs, provider API errors, or provider-specific request identifiers.

This applies to mobile screens, web screens, emails, notifications, toast messages, customer-visible logs, support codes, API responses, downloadable reports, screenshots, analytics event properties, and client-side error objects.

### 2. Keep public contracts provider-neutral

Public and mobile-facing APIs should use abstractions such as:

```ts
type DocumentProcessingStatus =
  | "uploaded"
  | "processing"
  | "ready"
  | "unsupported"
  | "too_large"
  | "invalid_file"
  | "processing_failed"
  | "temporarily_unavailable";
```

Use public error codes such as:

- `DOCUMENT_FILE_UNSUPPORTED`
- `DOCUMENT_FILE_TOO_LARGE`
- `DOCUMENT_PROCESSING_FAILED`
- `DOCUMENT_ANALYSIS_UNAVAILABLE`
- `DOCUMENT_ANALYSIS_FAILED`
- `DOCUMENT_MODEL_UNAVAILABLE`

Provider-specific errors may exist only inside the server-side provider adapter.

### 3. Sanitize provider errors at the server boundary

The backend may record the original provider response in protected operational telemetry, subject to redaction and retention rules.

Before returning an error to any client:

- remove provider names;
- remove API URLs;
- remove model IDs;
- remove provider file IDs;
- remove request IDs unless replaced with an application-owned support ID;
- remove provider documentation links;
- remove raw response bodies;
- map the error to a provider-neutral application code.

Example public error:

```ts
interface PublicDocumentError {
  code:
    | "DOCUMENT_FILE_UNSUPPORTED"
    | "DOCUMENT_FILE_TOO_LARGE"
    | "DOCUMENT_PROCESSING_FAILED"
    | "DOCUMENT_ANALYSIS_UNAVAILABLE"
    | "DOCUMENT_ANALYSIS_FAILED";
  message: string;
  retryable: boolean;
  supportReference: string;
}
```

`supportReference` must be generated by the application and must not be the provider request ID.

### 4. Do not leak provider metadata through successful responses

The mobile or public API response must not contain provider names, provider IDs, model IDs, resolved model identifiers, provider capabilities, provider file IDs, provider request IDs, provider status, provider base URLs, or raw provider responses.

Return only product-level data in `PublicDocumentAnalysisResult`:

```ts
interface PublicDocumentAnalysisResult {
  analysisId: string;
  status: "completed";
  documents: PublicAnalyzedDocument[];
  candidates: PublicAssetCandidate[];
  warnings: PublicAnalysisWarning[];
}
```

Keep provider provenance in protected server-side records.

### 5. Internal persistence may retain provider provenance

Operational and audit tables may retain provider identifiers, resolved model identifiers, provider file identifiers, provider request identifiers, provider response status, provider error categories, and upload/deletion timestamps.

These fields must be:

- inaccessible through customer RLS;
- excluded from mobile database types where practical;
- excluded from ordinary API serialization;
- excluded from public admin exports;
- visible only to authorized engineering or restricted operations roles;
- redacted from committed artifacts.

Prefer separate protected tables such as:

- `document_analysis_provider_runs`
- `document_analysis_provider_files`

Do not place provider metadata inside customer-readable `selected_facts_json`.

### 6. Keep provider-specific code isolated

Provider-specific implementation should be confined to a server-only adapter, for example:

```
packages/document-analysis-providers/server/
```

The rest of the application should depend on a provider-neutral interface such as:

```ts
interface NativeDocumentAnalysisProvider {
  resolveModel(): Promise<ResolvedDocumentModel>;
  uploadOriginalFile(input: OriginalFileInput): Promise<ProviderFileHandle>;
  analyze(input: NativeDocumentAnalysisRequest): Promise<unknown>;
  deleteFile(handle: ProviderFileHandle): Promise<void>;
}
```

Do not use provider names in mobile filenames, mobile imports, shared schema names, route names, public Edge Function names, customer-visible database objects, or analytics event names.

Acceptable internal server-only names may reference the concrete provider where required for implementation clarity.

### 7. Environment variables remain server-only

Use `KIMI_K3_API_KEY` only inside server-side execution.

Do not:

- prefix it with `EXPO_PUBLIC_`;
- expose it through runtime configuration endpoints;
- serialize environment configuration;
- include it in build output;
- include it in source maps;
- print whether the key is present;
- expose the resolved API base URL.

The client should know only that document analysis is available or unavailable.

### 8. Remove provider branding from processing states

Use provider-neutral processing states such as:

- "Preparing secure analysis"
- "Analyzing document"
- "Unsupported file"
- "File too large"
- "Document processing failed"

Do not display provider-branded states to customers.

### 9. Redact verification artifacts

Committed artifacts must not contain provider names, model names, API base URLs, provider file IDs, provider request IDs, or provider error text.

Use summaries such as:

```text
document provider configured: PASS
native original-file submission: PASS
files accepted: 4
analysis calls: 1
local conversion calls: 0
fallback calls: 0
temporary files deleted: PASS
```

Store detailed provider diagnostics only in ignored, access-controlled local artifacts.

### 10. Prevent indirect disclosure

Verify that provider identity cannot be inferred from response headers, upstream error formatting, status-page links, URLs embedded in errors, file-reference prefixes, network response payloads, client telemetry, Sentry breadcrumbs available to customers, generated filenames, support messages, UI screenshots, or PR descriptions intended for non-engineering review.

Proxy all provider communication through the application backend. The mobile client must never communicate directly with the provider domain.

### 11. Legal and compliance exception

Do not expose the provider as part of the normal product experience.

However, do not conceal legally required subprocessors or data-processing disclosures. Where privacy law, contractual terms, or a formal subprocessor list requires identification, disclose it only through the appropriate legal or compliance documentation—not through ordinary application UI or APIs.

### 12. Acceptance tests

Add tests proving:

- no provider name appears in the mobile bundle;
- no provider model ID appears in public API responses;
- no provider file ID appears in public API responses;
- upstream error messages are sanitized;
- response headers do not reveal the upstream host;
- public analytics events contain no provider identifiers;
- committed verification artifacts contain no provider identifiers;
- provider metadata tables are inaccessible to authenticated customers;
- the mobile client never contacts the provider domain directly;
- customer-facing states remain provider-neutral.
